## 1. Что хотим

Отдельная кнопка **«📈 Управление»** в главном меню бота, видна и доступна **только трём руководителям**.
По ней руководитель в любой момент одной-двумя кнопками получает актуальную картину по компании.
Данные берутся **напрямую из существующих Google-таблиц** (они постоянно обновляются командой) — ничего вручную не выгружаем.

Три блока (+ свободный вопрос к ИИ):

1. **📁 Проекты** — сколько проектов всего / активных / на паузе / закрытых; по отделам (разработка = дизайн-проекты,
   реализация = ремонт/стройка, комплектация); загрузка отделов и каждого сотрудника (активные проекты, м²);
   суммы контрактов, оплачено, остаток к получению; новые подписания за месяц.
2. **📊 Планы** — выполнение месячного плана по отделам: план / факт / % (накопительно на текущую неделю).
   Планы ставятся в начале месяца руководителями отделов с Александром, факт обновляется еженедельно на планёрке.
3. **👥 HR** — воронка найма по каждой роли: отклики → HR-скрининг → интервью → тестовое → оффер → выход,
   по неделям и источникам (HH, LinkedIn, Indeed, Hirify, Geekjob, LI reachouts, Socials), конверсии.
4. **💬 Спросить** — свободный вопрос текстом (или голосом — Whisper уже есть) по этим данным,
   например «сколько дизайн-проектов на паузе у Ильи и на какую сумму?».

Позже (не в первой итерации): **💰 Продажи** (подписанные контракты: с кем, сумма, дата — нужен отдельный лист),
маркетинг (лиды, стоимость лида — уже есть в план-факте), еженедельный авто-дайджест руководителям.

Принцип из встречи: «не ставить ради того, чтобы ставить» — только то, что реально нужно в моменте:
планы, проекты/загрузка, ключевые показатели. Дальше наращиваем.

## 2. Ключевые архитектурные решения

1. **Цифры по кнопкам считает код, а не ИИ.** Нажатие кнопки = детерминированный расчёт в Python → точно,
   одинаково при каждом нажатии и **0 токенов**. Claude не получает сырые таблицы на сотни строк.
2. **ИИ только для свободных вопросов — через tool use.** Claude получает инструменты
   (`get_projects`, `get_plan`, `get_hiring`, `get_workload`), вызывает их, код возвращает уже посчитанные/отфильтрованные данные,
   Claude формулирует ответ. Запрет выдумывать цифры — так же, как в «Базе знаний» (строго по данным).
3. **Доступ по Telegram user ID, а не по нику** (ник можно сменить/передать). Проверка в двух местах:
   кнопка не показывается в меню + каждый хендлер/колбэк раздела сам проверяет ID (иначе раздел откроет любой, кто знает команду/callback_data).
4. **Кэш 5 минут** на каждую таблицу (в памяти). Каждая таблица/лист читается одним запросом
   (`worksheet.get_all_values()` или `spreadsheet.values_batch_get`). Лимит Sheets API ~60 чтений/мин — с кэшем не упрёмся.
   Кнопка «🔄 Обновить» в разделе сбрасывает кэш принудительно. В каждом ответе — «данные на ЧЧ:ММ (Дубай)».
5. **gspread синхронный** → вызывать через `asyncio.to_thread(...)` (или как уже сделано в `app/sheets.py`), чтобы не блокировать long polling.
6. **Только чтение.** Боту на эти таблицы нужен доступ «Читатель», он в них ничего не пишет.

### 4.1. Мастер-таблица проектов «UAE … 2026»

Листы: `Настройки`, `Бронь номеров`, `Marketing`, `NPS`, `Общая таблица`, `Отдел разработки`,
`Загрузка (отдел разработки)`, `Отдел реализации`, `Загрузка отдела реализации`, `Отдел комплектации`, `Загрузка отдела комплектации`.

**`Общая таблица`** — главный источник для сводки. Строки 1–2 — сводка (`In progress 84`, `On pause 17`, `Design project 26`,
`Construction 12`, `Interior equipment 40` — это активные по типам). **Заголовок — строка 3**, данные с 4-й (~223 проекта). Колонки:
`Project number | Project name | Area, m2 | Project Type | Project Status | Project Stage | Responsible Designer |
Responsible architect | Responsible visualizer | Project manager/designer | Responsible foreman |
Date of signing the contract | Date of completion PLAN | Project Completion Date ACTUAL | Total Project Revenue | Client Satisfaction`

- `Project Type`: `Design project` (отдел разработки), `Construction` (отдел реализации), `Interior equipment` (отдел комплектации).
- Номер проекта, похоже, кодирует тип суффиксом: `-02` дизайн, `-03` комплектация, `-04` ремонт (один объект = несколько проектов,
  напр. `106-03` и `106-04`). Есть номера с префиксом `US` (США) и нестандартные (`Muse`, `MuseDesign`). Проверить с заказчиком.
- Суммы — в дирхамах (AED / dh).

**`Отдел разработки`** (дизайн): строки 1–5 — сводка по дизайнерам (`Number of projects | Ilya | Polina`, без подписей строк),
**заголовок — строка 6** (~104 проекта). Колонки: `Project number, Project name, Area m2, Project Type, Project Status, Project Stage,
Satisfaction, Responsible Designer, Responsible architect (чертежник), Responsible planner (планировка), Responsible visualizer (дизайнер),
Signing the contract Date, Project Completion PLAN Date, Project Completion Date, Contract Total, Paid, Remaining, % Paid,
Payment date/amount/receipt mark 1…8, Collect NPS, Дебиторка итого`.

**`Отдел реализации`** (ремонт): заголовок — строка 6 (~40 проектов). Сводка сверху по `Polina | Vladimir | Meerim`.
Колонки: `…, Project Type, Столбец 5 (это фактически статус — заголовок не подписан!), Project Stage, Project manager, Responsible foreman,
Date of signing the contract, Date of Permit Issuance, Date of completion PLAN, Completion ACTUAL, Дата ОС (+2 мес), ОС отправлена в NPS,
Collect NPS - Midway, Collect NPS - Final, Total Project Revenue, Total Project Cost AED PLAN, Client Satisfaction, Payment 1…9`.

**`Отдел комплектации`**: заголовок — строка 6 (~79 проектов). Сводка сверху по `Ansia | Alena | Tatiana | May | Alina`.
Колонки: `…, Project Status, Project Stage, Responsible FF&E designer, Date of signing, Completion PLAN, Completion ACTUAL,
Total Project Revenue, Total Project Cost AED PLAN, Client Satisfaction, Payment 1…10, Funds received, Balance to be received`.

**Листы «Загрузка …»** — уже посчитанная загрузка, можно брать готовое:
- `Загрузка (отдел разработки)`: `Designer | Projects now | Current area m² | Remaining payment now | Total projects in progress | Total area in use | Total balance of payments`
  (сейчас: Ilya 13 / 5133 м² / 261 126; Polina 9 / 1659 м² / 200 457; всего 22 / 6792,5 м² / 461 582). Заголовок примерно в строке 5.
- `Загрузка отдела реализации`: `Project manager | Projects now | Current area m² | Projects on pause | Square` + строка Total;
  ниже — помесячная динамика «Projects in progress this month» и «Area under work per month» (12 колонок-месяцев) по каждому ПМ.
- `Загрузка отдела комплектации`: `Designer | Projects now | Current area m² | Equipment | Commission | Author's supervision` + строка «Всего».

**Решение для v1:** сводку «Проекты» считать кодом из `Общая таблица` (+ листы отделов для денег: оплачено/остаток),
загрузку по людям — брать с листов «Загрузка …» (это «официальные» цифры отделов) и сверять с собственным расчётом;
при расхождении — показывать цифру листа «Загрузка» (и логировать расхождение админу, не руководителям).

**Важно из встречи:** загрузка комплектации может «считаться некорректно» не из-за формул, а потому что сотрудники
не проставляют даты на листах отделов. Бот это не исправит, но может подсветить (см. п. 8, «Контроль заполнения»).

### 4.2. Таблица план-факт «… планов»

Листы: `ПЛАН ДЕКАБРЬ`, `ПЛАН НОЯБРЬ`, `ПЛАН ОКТЯБРЬ`, `ПЛАН СЕНТЯБРЬ`, `ПЛАН АВГУСТ`, `Дашборды` (пустой).
Имя листа = `ПЛАН <МЕСЯЦ ЗАГЛАВНЫМИ>` — по нему выбираем месяц (год в имени не указан!).

Структура листа:
- Строка 1: `Роль | Показатель | План на месяц | Неделя 01.10 - 02.10 | … | Неделя 26.10 - 31.10` — заголовки недель объединены на 4 колонки
  (недель 5–6, начало блока недели: D, H, L, P, T…).
- Строка 2: внутри каждой недели `Факт` (2 объединённые колонки) и `% плана месяца (накоп.)` (2 объединённые колонки).
  То есть на неделю: факт = колонка начала блока, % накоп. = начало блока + 2.
- Данные с 3-й строки. **Колонка «Роль» (отдел) заполнена только в первой строке блока** → протягивать вниз.

Отделы и показатели (октябрь, план):
- **Маркетинг:** Лиды Дубай SQL (35), Лиды Дубай MQL (62), Лиды США SQL (20), Лиды США MQL (32), Клиенты (11), Привлечённые деньги (650 000),
  Бюджет на лиды Дубай (25 000), Бюджет на лиды США (15 000), Стоимость SQL/MQL Дубай/США (расчётные).
- **Отдел продаж:** Сделки (19), Сумма новых контрактов dh (600 000), Новые подписания (15), Сумма контрактов доподписания (1 800 000),
  Доподписания (4), Количество встреч (55), Количество КП (60), Горячие лиды (25).
- **Дизайнер — Илья:** Сданные м² (2275), Полученные деньги dh (134 470), Кол-во сданных проектов (3).
- **Дизайнер — Полина:** Сданные м² (414), Полученные деньги dh (75 684), Кол-во сданных проектов (1).
- **Отдел реализации:** Сданные объекты (план пустой), Полученные деньги dh (926 142).
- **Отдел комплектации:** Выработанные деньги dh (2 101 142).
- **HR:** План найма чел (4), Публикации/вакансии (4), Интервью (18), Офферы высланные (4), Выведено людей (4).
- **Финансист:** Кол-во внедрённых операционных задач/проектов (6).
- **Бизнес-ассистент:** Кол-во внедрённых операционных задач/проектов (12).

Правила расчёта:
- **% выполнения считать самим:** `сумма фактов по заполненным неделям / план`. Не доверять колонке «% накоп.» последней недели:
  в октябре у пустой последней недели % ниже предыдущего (напр. SQL Дубай 14% → 9%) — формула ломается на пустом факте.
  Колонку «% накоп.» можно использовать для сверки.
- «Текущая неделя» = последняя неделя, где есть хоть один факт.
- **Обратные показатели** (стоимость лида, бюджеты): меньше = лучше, для них не показывать «% выполнения» как достижение —
  показывать «факт vs план» и отметку «в рамках / превышен».
- **Расчётные показатели** (стоимость SQL/MQL = бюджет / лиды) — брать как есть из таблицы или пересчитывать, не суммировать по неделям.
- Деньги (`Привлечённые деньги`, `Полученные деньги`, суммы контрактов) — суммируются по неделям.
- Пустой план → показывать «план не задан», не делить на ноль.
- Статус: 🟢 ≥ ожидаемого темпа, 🟡 отставание до ~15 п.п., 🔴 больше. Ожидаемый темп = доля прошедших рабочих дней месяца
  (так 40% в середине месяца — нормально, а 40% в конце — плохо). Пороги — уточнить у заказчика.
- **Грабли:** листы `ПЛАН НОЯБРЬ` и `ПЛАН ДЕКАБРЬ` скопированы с сентября — в заголовках недели `01.09 – 30.09`, план пустой.
  Пока план не заполнен → бот пишет «план на ноябрь ещё не внесён». Даты недель парсить из заголовка регуляркой `\d\d\.\d\d`;
  если месяц в датах не совпадает с месяцем листа — предупреждать админа (не руководителей).
  В `ПЛАН АВГУСТ` лишняя колонка с датой `31.08` вместо «Неделя …» и неполная разметка Факт/% — парсер не должен падать.

### 4.3. Таблица найма `hiring_pipeline`

Листы по месяцам: `september`, `october`, `november` (пустой). Каждый лист — **блоки по горизонтали (неделя) и вертикали (роль)**:
- Блок недели шириной 10 колонок (A–J, K–T, U–AD …). В строке 1 начала блока — диапазон дат (` 12.10 - 16.10.2026`).
- Внутри — блоки ролей по 10 строк с шагом: строка 1 блока — название роли (`Sales USA`, `Civil Engineer`, `CMO`, `Conceptologist`, `Recruiter`, …),
  далее `priority/comments` (значение в соседней ячейке, напр. `high/`), `sources | HH | Linked In | Indeed | Geekjob | LI reachouts | Socials | Total | Conversion`,
  затем этапы-строки: `responses`, `HR screening`, `1st step interview` (в сентябре — `test assignment`), `tech interview`, `offer`, `joining`.

Грабли (парсить по ячейкам-якорям, а не по фиксированным адресам):
- **Названия ролей меняются от недели к неделе:** `Sales USA` → `Sales manager USA`, `Civil Engineer` → `Civil Engineer Dubai`,
  `CMO` → `CMO remote`; в одной и той же позиции может стоять другая роль (`Дизайнер экстерьеров` в одной неделе, `Recruiter` в следующей).
  → Нужен словарь синонимов ролей (уточнить у HR) и сопоставление по названию, а не по позиции.
- **Набор и порядок источников различается** (в одном блоке колонка D — `Indeed`, в другом — `Hirify`) → брать имена источников из строки `sources` каждого блока.
- **Набор этапов различается** (`test assignment` vs `1st step interview`) → брать по названию строки.
- **`Total` и `Conversion` местами не посчитаны или неверны** (Conversion 126%, пустой Total) → **пересчитывать самим**
  из ячеек источников; конверсию считать от `responses` этого же блока.
- Неделя может переходить месяц (`23.09 - 02.10.2026`).

**Рекомендация заказчику** (не блокер): перевести найм в «длинный» формат на отдельном листе —
одна строка = `неделя | роль | источник | этап | количество`. Людям вести так же просто, а парсинг становится надёжным.
v1 делаем на текущем формате с парсером блоков; если таблицу переведут — парсер заменяется.

## 5. Нормализация данных (обязательно — иначе цифры разойдутся)

- **Статусы:** `In progress` и `In Progress` → `in_progress`; `On Pause`/`On pause` → `paused`; `Completed` → `completed`;
  `The client refused` и `Rejections` → `refused`; `New` → `new`; пусто → `unknown`. Сравнение без учёта регистра и пробелов.
  Сейчас по `Общая таблица`: всего 223, в работе 84 (59 + 25), на паузе 17 (13 + 4), завершено 105, отказы 15, новый 1 —
  совпадает со сводкой в шапке листа (84 / 17) → это тест на корректность нормализации.
- **Типы:** `Design project` → разработка, `Construction` → реализация, `Interior equipment` → комплектация. 6–7 проектов без типа —
  считать в «без типа» и показывать отдельной строкой, не терять.
- **Ошибки/мусор в ячейках:** `#N/A`, `??`, пустые строки, числа-даты (Excel-серийные `46079` вместо даты) → `None`/парсинг.
  Площадь и суммы — `float` с удалением пробелов/запятых; нечисловое → `None` (не 0!) и в счётчик «данные не заполнены».
- **Номера проектов:** `strip()` (встречается `' 327-02'`).
- **Имена сотрудников:** латиница в мастер-таблице (`Ilya`, `Polina`, `Meerim`, `Vladimir`, `Ansia`, `Alena`, `Tatiana`, `May`, `Alina`),
  кириллица в боте/команде TEAM (`Ансия`, `Алена`…) — единый словарь соответствия. В мастер-таблице проджекты отдела реализации включают
  значение `Without a project` — это не человек, исключать из загрузки.
- **«Polina»** встречается и как дизайнер (разработка), и как ПМ (реализация) — уточнить у заказчика, один это человек или два.
  Tatiana есть в комплектации мастер-таблицы, но её нет в TEAM бота — уточнить.
- Чтение через `get_all_values()` даёт строки → для дат и чисел лучше `value_render_option='UNFORMATTED_VALUE'`
  и `date_time_render_option='FORMATTED_STRING'` (или парсить оба варианта).

## 7. «💬 Спросить» — Claude с инструментами

- Функция в `app/claude_answer.py`, токены — через `app/billing.py` (чтобы траты были видны в «💰 Баланс»).
- Модель: по умолчанию та же `claude-haiku-4-5`; через `MGMT_MODEL` можно поставить более сильную модель только для этого раздела,
  если ответы на аналитические вопросы окажутся слабыми (проверить актуальные ID моделей).
- Инструменты (возвращают компактный JSON, уже нормализованный и отфильтрованный — не всю таблицу):
  - `get_projects(department?, status?, person?, signed_from?, signed_to?)` → список проектов (номер, название, тип, статус, этап, м², сумма, оплачено, остаток, ответственные) + агрегаты.
  - `get_workload(department?)` → загрузка по сотрудникам.
  - `get_plan(month, department?)` → показатели план/факт/% по неделям.
  - `get_hiring(role?, month?, week?)` → воронка по ролям/источникам.
- Системный промпт: отвечай только по данным инструментов; если данных нет — так и скажи; не округляй деньги «на глаз»;
  указывай, за какой период/на какую дату цифры; кратко, по-деловому, на языке вопроса.
- Голосовой вопрос: тот же Whisper-пайплайн, что в «Договорённостях».
- Ограничить число итераций tool use (напр. 5) и длину ответа.

## 8. Надёжность и обработка ошибок (в стиле бота)

- Таблица недоступна / нет доступа / лист не найден → руководителю: «Не удалось получить данные из таблицы, админ уже знает»;
  админу через `app/notify.py`: какая таблица, какая причина (нет доступа для почты сервисного аккаунта / не найдена / квота).
- Если кэш есть, а обновить не удалось — показать данные из кэша с пометкой «данные на ЧЧ:ММ, обновить не удалось».
- Сбой Claude в «Спросить» → понятное сообщение, кнопки разделов продолжают работать (они без ИИ).
- Логи — в journalctl, как у остального бота.
- **Контроль заполнения (полезный побочный эффект):** при парсинге собирать проблемы данных — проекты без типа/статуса, `#N/A`,
  пустые даты на листах отделов (особенно комплектация), листы плана с чужими датами. Админу — команда `/mgmt_check`;
  позже — еженедельная сводка «что не заполнено» ответственным, чтобы загрузка считалась корректно.

## 9. Доступ к таблицам — проверить ПЕРВЫМ

1. Открыть каждую из трёх таблиц → «Настройки доступа» → добавить email сервисного аккаунта (из `google_credentials.json`, поле `client_email`) с правом **«Читатель»**.
2. **Известная грабля:** корпоративный Google Workspace может запрещать делиться с внешней почтой бота.
   Мастер-таблицу ведёт вся команда, поэтому вариант «пересоздать в личном аккаунте» здесь не подходит.
   Решение — администратор Workspace разрешает внешний доступ для этого одного адреса
   (или добавляет его в список доверенных). Сделать до начала разработки.
3. ID таблицы — часть ссылки между `/d/` и `/edit`.
4. Сделать команду админа `/mgmt_ping` — проверяет доступ ко всем трём таблицам и всем нужным листам, отвечает списком ✅/❌.

## 10. План работ (итерации)

1. **Каркас:** `/myid`, `MGMT_IDS`, кнопка «📈 Управление» только для них, пустое подменю, `/mgmt_ping`.
2. **Проекты:** чтение мастер-таблицы, нормализация, сводка, по отделам, загрузка по людям, новые подписания. Тест: 84 в работе / 17 на паузе.
3. **Планы:** парсер листов `ПЛАН <МЕСЯЦ>`, выбор месяца, по отделу и общая сводка, статусы 🟢🟡🔴.
4. **HR:** парсер блоков, словарь ролей, воронка за неделю и месяц.
5. **Спросить:** Claude + инструменты, голос.
6. **Обновить `HANDOFF.md`**, проверить RU/EN, показать руководителям, собрать правки.
7. Потом: Продажи (лист «Контракты»), маркетинг отдельной кнопкой, авто-дайджест руководителям в понедельник утром
   перед планёркой (механизм напоминаний уже есть; это отдельное решение — сейчас правило «руководителю бот не пишет» касается расходов).

Тесты: вынести расчёты в чистые функции `management_data.py` и прогнать их на xlsx-выгрузках / сохранённых `get_all_values()` снимках
(положить фикстуры в `tests/fixtures/`, **без реальных персональных данных клиентов в git**, либо держать вне репозитория).

## 11. Деплой (для Николая, по одной команде)

1. Добавить в `/root/CorporateBot/.env` строки `MGMT_*` (дать готовыми значениями).
2. `cd /root/CorporateBot && git pull`
3. `systemctl restart corporatebot`
4. Подождать 1–2 минуты (бот загружается), затем в Telegram `/mgmt_ping`.
5. Если что-то не так: `journalctl -u corporatebot -n 100`.

Новых зависимостей не требуется (gspread и anthropic уже есть).
